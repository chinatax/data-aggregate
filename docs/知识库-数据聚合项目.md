## 一、项目概述

DataAgg 是一个部署在阿里云 ECS 上的全栈 A 股市场数据聚合平台。它从腾讯财经、东方财富、同花顺、财联社等多家外部数据源定时拉取行情、快讯、热点、资金流向、龙虎榜、股东户数等数据，经过清洗、补全、缓存后通过 RESTful API 提供给前端。平台同时集成了博客系统（支持 Markdown 编辑与代码高亮）、电子书集（~1000+ 本 Markdown 书籍，支持分类浏览与收藏下载）、以及管理后台（系统监控、站点配置、分类管理）。整个项目采用前后端分离架构，后端为 Spring Boot Maven 多模块工程（84 个 Java 文件），前端为 Vue 3 + TypeScript + Vite 单页应用（42 个源文件），通过 Docker Compose 在单台 ECS 上编排 MySQL、Redis、Nginx、Spring Boot 四个核心服务。

| 维度 | 说明 |
|------|------|
| 项目类型 | 全栈 Web 应用（前后端分离） |
| 核心领域 | A 股行情数据聚合 + 内容管理（博客/电子书） |
| 部署地址 | `https://112.124.35.167` (阿里云 ECS) |
| 代码规模 | 后端 84 个 Java 文件 + 前端 42 个源文件 |
| 数据库 | 20 张业务表，10 个 SQL 初始化脚本 |
| 外部数据源 | 腾讯财经、东方财富、同花顺、财联社、hexin.cn、newsdata.io |

## 二、技术栈

项目技术选型围绕三个目标：**后端稳定可靠**（Spring Boot 3 + MyBatis-Plus + MySQL）、**前端开发现代化**（Vue 3 Composition API + TypeScript + Element Plus）、**运维简单可控**（Docker Compose 单机部署，无 Kubernetes 复杂度）。

后端以 Spring Boot 3.2.5 为核心框架，Maven 多模块分层管理。持久层使用 MyBatis-Plus 3.5.7，利用其自动填充、逻辑删除、Lambda 查询等特性减少样板代码。缓存采用 Caffeine（L1 本地）+ Redis（L2 分布式）两级架构，确保热数据毫秒级响应。安全层使用 JWT 无状态认证 + BCrypt 密码加密，拦截器配合自定义注解 `@RequireAuth` 实现声明式权限控制。外部数据抓取使用 RestTemplate 直连 HTTP API，Jackson 解析 JSON 响应，jsoup 处理 HTML 页面抓取。

前端以 Vue 3.5 为框架，全面使用 Composition API + `<script setup>` 语法。TypeScript 提供类型安全，Vite 提供秒级热更新。UI 库选用 Element Plus 2.x 并全量注册图标组件，通过 SCSS 变量覆盖实现统一的灰色调主题。状态管理使用 Pinia 拆分为 auth/site/app 三个 Store。Axios 封装了 Bearer Token 注入、响应自动解包、401 重定向、GET 请求去重等能力。Markdown 编辑器支持编辑/分屏/预览三种模式，集成图片拖拽上传、URL 抓取导入、代码块语言选择等功能。

## 三、项目结构

项目根目录下划分三个核心区域：`backend/` 承载全部 Java 代码，按 Maven 多模块分为 common（共享模型）、service（业务逻辑）、start（启动入口）三层；`frontend/` 承载 Vue 3 单页应用，按职责分为 api（接口层）、components（公共组件）、views（页面视图）、stores（状态管理）、router（路由）等目录；`docker/` 承载所有基础设施配置，包括 MySQL 建表脚本、Nginx 反向代理配置、Redis 配置。此外 `book/` 目录存放 ~1000+ 本 Markdown 格式电子书，通过文件系统挂载到后端容器供解析和搜索。

后端三模块依赖关系为：`dataagg-start → dataagg-service → dataagg-common`。common 层定义 20 个 Entity 实体和 19 个 DTO/VO 传输对象，service 层包含 20 个 Mapper 接口和 22 个 Service 业务类，start 层包含 15 个 Controller、7 个配置类、3 个定时调度器。这种分层确保了模型复用（common 可被任意模块依赖）、业务逻辑独立可测试（service 不依赖 Web 层）、以及启动配置集中管理。

## 四、核心功能模块

平台功能分为四大板块：**首页仪表盘**（9 个 A 股数据模块，覆盖行情、资金、龙虎榜、筹码等维度）、**博客系统**（Markdown 编辑/发布/评论）、**电子书集**（分类浏览/搜索/收藏/下载）、**管理后台**（系统性能监控/站点配置/分类管理/书籍增量监控）。

首页仪表盘是本项目的核心亮点。顶部 IndexBar 滚动展示 20 个主要指数的实时涨跌；中部分为左右双列——左侧轮播财联社快讯（红色高亮），右侧展示东财全球资讯；下方列出当日热点题材股，每只股票附有同花顺编辑部人工运营的题材归因标签（如"算力租赁+AI政务"）来解释上涨原因；北向资金模块实时显示沪股通/深股通的分钟级净买入金额；融资融券模块展示当日两融余额并附带 30 日历史趋势图（SVG 内联绘制）；龙虎榜列出全市场当日上榜股票，含买入/卖出金额和净买额排名，支持分页浏览；连板天梯按首板、二板、三板及以上三个标签页分类展示涨停股票，每只股票标注连板数和题材原因；最底部筹码集中模块展示股东户数环比减少最多的 Top 100 股票，含行业和地区信息，支持翻页浏览。为优化首页加载性能，折叠线以下模块采用 IntersectionObserver 懒加载，仅在滚动进入视口时才发起 API 请求。

## 五、Skill 数据源与提取方式

本项目以 `a-stock-data` Skill 定义的数据源体系为参考蓝本，但将 Python 实现完全替换为 Java 原生 HTTP 直连，做到**零第三方 Python 依赖**。所有数据抓取均在 `StockDataService` 中统一管理，遵循相同的处理管线：通过 RestTemplate 发起 HTTP GET 请求（带 User-Agent 和 Referer 头模拟浏览器），获取响应后用 Jackson ObjectMapper 解析为 JsonNode 树，按字段路径逐一提取、清洗、转换为 Entity 实体，最后经由 MyBatis-Plus 写入 MySQL、Jackson 序列化写入 Redis、同步更新 Caffeine L1 缓存。

数据源覆盖 Skill 定义的四个层级。**行情层**使用腾讯财经 API（`qt.gtimg.cn`）拉取 20 个指数实时价、涨跌额、涨跌幅，GBK 编码以 `~` 分隔 88 个字段；**信号层**从同花顺拉取热点题材（含 `reason` 人工运营标签），从 hexin.cn 拉取北向资金分钟流向，从东财 push2 拉取行业板块排名，从东财 datacenter 拉取龙虎榜和限售解禁；**资金/筹码层**从东财 datacenter 拉取融资融券、股东户数变化（`RPT_HOLDERNUMLATEST` 报表），再通过东财 F10 接口（`CompanySurveyAjax`）逐股补全行业（`sshy`）和地区（`qy`）字段；**新闻层**从财联社（`cls.cn`）拉取实时电报，从东财（`np-weblist`）拉取 7×24 全球资讯。

最复杂的两个数据模块是**连板天梯**和**筹码集中**。连板天梯需要先扫描全市场当日涨停股，再逐个查腾讯 K 线历史数据计算连续涨停天数，属于计算密集型操作。筹码集中需要先拉取全市场最新报告期的股东户数数据，筛选环比变化为负（`HOLDER_NUM_RATIO < 0`）的股票取 Top 100，再逐个调用 F10 接口补全行业和地区信息，调用间隔设为 300ms 以防止东财服务端限流。

## 六、三级缓存架构

为了在高频刷新（指数 30s、快讯 60s）和大数据量查询（股东户数 100 条、龙虎榜全市场）之间取得平衡，系统设计了三级缓存体系：**L1 Caffeine 本地缓存**（JVM 堆内，读取耗时 <1μs）、**L2 Redis 分布式缓存**（网络 IO，读取耗时 ~1ms）、**L3 MySQL 持久化存储**（磁盘 IO，读取耗时 ~10ms）。

L1 和 L2 均设置带 TTL 的自动过期。L1 Caffeine 的 TTL 配置较短（20~60s），仅作为突发流量的缓冲层，避免 Redis 被瞬间击穿；L2 Redis 的 TTL 与数据刷新频率匹配（60~600s），作为主要的读缓存层；L3 MySQL 承担持久化角色，部分数据（连板天梯）永久保留，大部分数据由凌晨 3:05 的清理任务按策略删除。

读请求遵循标准的 Cache-Aside 穿透模式：先查 L1 Caffeine，命中直接返回；未命中则查 L2 Redis，命中后回写 L1 再返回；仍未命中则查 L3 MySQL，有数据则依次回写 L2 和 L1 后返回。写请求（定时抓取）采用 Write-Behind 策略：先更新 MySQL（持久化保证），再更新 Redis（设置 TTL），最后更新 Caffeine（覆盖或失效）。

值得注意的设计是：并非所有数据都走满三级缓存。指数行情和北向资金只存 Redis（不落 MySQL），因为这类实时数据没有回溯价值，每次抓取覆盖即可；融资融券同理，仅保留 Redis 中的最新快照；而股东户数这类季度级低频数据则 L1 TTL 设为 60s、L2 TTL 设为 600s，以空间换时间减少对外部 API 的调用。

### 缓存层级

```
L1: Caffeine (JVM 堆内, <1μs)   ← 20~60s TTL
L2: Redis (网络 IO, ~1ms)       ← 60~600s TTL
L3: MySQL (磁盘 IO, ~10ms)      ← 永久 / 定期清理
```

### 读穿透流程

```
请求 → L1.get()
  ├─ 命中 → 返回
  └─ 未命中 → L2 Redis.get()
       ├─ 命中 → L1.put() → 返回
       └─ 未命中 → L3 MySQL 查询
            ├─ 有数据 → L2.set() + L1.put() → 返回
            └─ 无数据 → 返回空
```

## 七、后台数据表结构

数据库 `data_aggregate` 共 20 张表，分为股票数据（8 张）和业务数据（12 张）两大类。所有表使用 InnoDB 引擎、utf8mb4 字符集，金额字段统一使用 DECIMAL 类型保证精度，时间字段统一使用 DATETIME/LocalDate。

**股票数据表**承载从外部数据源抓取的全部 A 股相关数据。`stock_news_flash` 和 `stock_global_news` 分别存储财联社快讯和东财全球资讯，通过唯一约束（news_id / news_code）防止重复入库。`stock_hot_topic` 记录每日热点题材股及其归因标签，`stock_industry_rank` 记录行业板块的涨跌排名快照。`stock_dragon_board` 存储龙虎榜上榜记录，含净买额、买卖金额、换手率等指标，通过 (code, trade_date) 联合唯一键保证同一天同一只股票不重复。`stock_board_daily` 存储连板天梯数据，核心字段 `board_count` 记录每只股票的连续涨停天数。`stock_lockup_expiry` 存储限售解禁日历，按解禁日期索引。`stock_holder_num` 存储股东户数变化数据，其中 `industry` 和 `region` 字段并非来自原始 API（`RPT_HOLDERNUMLATEST` 不提供），而是后续通过 F10 接口补全的增强数据。

**业务数据表**支撑博客、电子书、用户、评论、站点配置等功能。`user` 表密码经 BCrypt 编码存储，支持微信 OpenID 关联。`comment` 表通过 `parentId` 自引用实现嵌套回复树。`book_file_hash` 表记录每本电子书文件的 MD5 哈希，配合 `book_monitor_log` 实现文件变更的增量监控（新增/修改/删除数量统计）。`site_setting` 表采用 key-value 模式存储站点动态配置，按 `groupName` 分组管理。

## 八、定时任务调度

系统的数据新鲜度由三组定时调度器保证，全部基于 Spring `@Scheduled` 注解实现（`SchedulingConfig` 开启 `@EnableScheduling`）。

**StockDataScheduler** 是核心调度器，管理 13 个任务方法。每个任务对应一个数据模块，拥有独立的初始延迟和执行间隔，全部通过 `application.yml` 中的 `stock.*.initialDelay` 和 `stock.*.interval` 属性可配置。12 个数据抓取任务在启动时错开初始延迟（5s~40s），避免同时发起大量外部 HTTP 请求。执行频率按数据变化速度分级：指数行情最快（30s），快讯和北向资金次之（60s），热点和行业排名中等（300s），限售解禁和股东户数最慢（3600s 和 1800s，因为解禁日历按天变动、股东户数按季度变动）。此外还有一个 `cleanOldData()` 任务在每天凌晨 3:05 执行，按不同保留策略清理 7 类过期数据——快讯和全球资讯仅保留 3 天（时效性极强），龙虎榜和行业排名保留 7 天，热点题材保留 30 天（题材归因有回溯价值），限售解禁到期即删，股东户数保留 365 天（支持年度对比），连板天梯**不清理**（唯一永久保留的股票数据）。

另外两组调度器：**BookMonitorScheduler** 每小时扫描 `book/` 目录，计算每个 Markdown 文件的 MD5 哈希与数据库比对，识别新增/修改/删除的文件并自动同步到 `book` 表；**NewsFetchScheduler** 每 10 分钟从 newsdata.io API 抓取 10 个分类 + 7 个税务查询的国际新闻。

应用启动时，**StockDataWarmup**（实现 `ApplicationRunner`）通过 `CompletableFuture.runAsync()` 异步并行调用全部 12 个 `fetchAndCache*()` 方法，确保容器启动后首批缓存数据在 5 秒内就绪，用户打开首页无需等待。

## 九、API 接口总览

系统通过 `StockV2Controller` 暴露 12 个股票数据端点（统一前缀 `/api/stock/v2`），外加 9 组业务 API 覆盖认证、博客、电子书、新闻、分类、系统监控、站点配置、上传、税务等场景。所有 API 返回统一响应体 `Result<T> { code, msg, data }`，前端 Axios 拦截器自动解包 `data` 字段，对调用方透明。

股票 V2 接口全部为公开 GET 请求（无需认证），其中 `/market` 是聚合端点，一次返回指数、快讯、热点、统计四类数据，服务首页首屏加载。`/margin/history` 返回近 30 日融资融券逐日数据供前端绘制 SVG 趋势图。`/board-ladder` 返回三维结构（firstBoard / secondBoard / thirdPlusBoard），前端按标签页分别渲染。`/holder-num` 返回 100 条股东户数减少最多的股票，按 `changeRatio` 升序排列。

## 十、前端组件体系

前端采用 Vue 3 Composition API 构建，组件树以 `App.vue` 为根，主布局 `layout/index.vue` 包含全局顶栏 `AppHeader` 和 `<router-view>` 插槽，编辑器使用独立的全屏布局 `EditorLayout.vue`。全局顶栏从 `siteStore` 动态读取频道列表（由管理后台配置），用户区域根据 `authStore` 的登录状态切换显示（未登录显示登录按钮，已登录显示头像下拉菜单含管理入口和退出）。

**公共组件（5 个）**：`AppHeader` 负责顶栏导航和用户菜单；`IndexBar` 是首页专用的滚动指数行情条，每 30s 轮询最新数据，鼠标悬停暂停滚动；`CommentSection` 实现嵌套评论树，支持根评论和子回复两级结构，使用确定性颜色哈希为匿名用户生成头像背景色；`RequireAuth` 是一个条件插槽包装器，通过 `authStore.isLoggedIn` 和可选 `role` 参数控制子内容的显示与隐藏，广泛用于管理入口和编辑按钮的权限控制。

**首页懒加载**：首页包含 9 个数据模块，全部加载会同时发起大量 API 请求。解决方案是使用 `IntersectionObserver` 监听折叠线以下的模块容器（龙虎榜、连板天梯、筹码集中、融资图表），仅在元素进入视口时才触发对应的数据请求，首屏只加载指数、快讯、热点三个模块。

**状态管理（3 个 Pinia Store）**：`authStore` 管理 JWT Token（localStorage 持久化）、用户信息、登录/注册/微信扫码/退出等动作；`siteStore` 在应用启动时从 `/api/site/config` 拉取站点动态配置（品牌名、导航频道、模块描述、配色等），并暴露一系列 computed 属性供组件直接使用；`appStore` 管理侧边栏折叠、页面标题等 UI 辅助状态。

**Axios 封装**：`utils/request.ts` 创建的 Axios 实例配置了 30s 超时、自动注入 Bearer Token、响应拦截自动解包 `data` 字段、401 状态码重定向到登录页、以及对相同 GET 请求的内置去重（并发时共享同一个 Promise）。

## 十一、部署架构

系统部署在阿里云 ECS 单机上（`112.124.35.167`），通过 Docker Compose 编排 4 个容器服务：**Nginx**（反向代理 + 静态文件服务，80/443 端口）、**Spring Boot Backend**（API 服务，8081 端口，prod profile）、**MySQL 8.0**（主数据库，3306 端口，持久化卷 `mysql_data`）、**Redis 7 Alpine**（缓存服务，6379 端口，持久化卷 `redis_data`）。所有服务接入同一个 Docker bridge 网络 `dataagg-network`，backend 和 nginx 通过 `depends_on` 声明启动依赖。

**请求路由**：用户请求 → Nginx:443（SSL 终端）→ 静态文件匹配（`/` 映射到 `frontend/dist`）→ 未匹配则代理到 `backend:8081`（`/api/*`、`/uploads/*`）。这种部署方式使得前端更新只需替换 `frontend/dist/` 目录内容（Nginx 卷挂载），无需重新构建后端镜像。

**数据持久化**：MySQL 数据通过命名卷 `mysql_data` 持久化，初始化脚本 `docker/mysql/init/*.sql` 在容器首次启动时自动执行建表。Redis 数据通过 `redis_data` 卷持久化，配置文件 `redis.conf` 挂载到容器。后端容器挂载两个主机目录：`./uploads`（用户上传图片）和 `./book`（电子书 Markdown 源文件），确保容器重建后数据不丢失。

**构建与部署流程**：后端通过 `Dockerfile` 多阶段构建（Maven 编译 → 精简 JRE 镜像），生产部署时执行 `docker compose -f docker-compose-prod.yml build --no-cache backend && up -d`；前端在本地执行 `npm run build` 后通过 SCP 将 `dist/` 上传到服务器并复制到 `/opt/dataagg/frontend/dist/`（Nginx 卷挂载点）。

## 十二、数据流程

整个系统的数据流可以分为**上行链路**（外部数据抓取入库）和**下行链路**（API 查询响应）两条主线，二者通过三级缓存实现解耦——定时任务负责上行（写入缓存），HTTP 接口负责下行（读取缓存），彼此互不阻塞。

**上行链路**：12 个 `@Scheduled` 任务按各自频率独立触发 → `StockDataService.fetch*()` 方法通过 RestTemplate 向外部 API 发起 HTTP GET 请求（携带 UA/Referer 头模拟浏览器）→ Jackson 解析 JSON 响应为 Entity 实体 → MyBatis-Plus 批量写入 MySQL（持久化保证）→ Jackson 序列化为 JSON 写入 Redis（设置 TTL）→ 更新 Caffeine L1 缓存。如果某次抓取失败（外部 API 不可用或限流），`log.warn` 记录告警但不影响下次调度，缓存层保留上一轮成功数据作为降级。

**下行链路**：用户浏览器发起请求 → Nginx 反代到 Spring Boot Controller → `AuthInterceptor` 校验 JWT（公开接口跳过）→ Controller 调用 `StockDataService.get*FromCache()` → L1 Caffeine 命中直接返回 → 未命中则 L2 Redis 命中返回 → 仍未命中则 L3 MySQL 查询并回写 → 统一封装 `Result<T>` 返回 → 前端 Axios 拦截器自动解包 `data` → Vue 响应式渲染。整套链路的可用性由缓存兜底：即使外部 API 全部故障，只要 Redis/MySQL 中还有上一轮数据，前端就能正常展示（只是数据略有过期）。

### 上行链路（数据抓取）

```
@Scheduled 触发
  → RestTemplate HTTP GET (UA/Referer)
  → Jackson JsonNode 解析
  → Entity 转换 + 清洗
  → MyBatis-Plus saveBatch → MySQL
  → Jackson → Redis (TTL)
  → Caffeine L1 put
  → 失败时 log.warn + 保留旧缓存
```

### 下行链路（API 查询）

```
浏览器 → Nginx → Controller
  → AuthInterceptor (JWT 校验)
  → Service.get*FromCache()
    → L1 Caffeine → 命中返回
    → L2 Redis → 命中回写L1返回
    → L3 MySQL → 命中回写L2+L1返回
  → Result<T> 统一响应
  → Axios 解包 data → Vue 渲染
```

## 十三、安全与认证

系统采用 JWT 无状态认证 + BCrypt 密码加密的安全方案。用户登录后服务端签发 JWT Token（HMAC-SHA 签名，7 天有效期），前端存入 `localStorage` 并在每次请求时通过 Axios 拦截器自动注入 `Authorization: Bearer <token>` 头。后端 `AuthInterceptor` 拦截所有 `/api/**` 请求（排除 `/api/auth/**`），解析 Token 提取 userId、username、role 并存入 `request.setAttribute`，Controller 层通过自定义 `@RequireAuth` 注解声明式校验（支持 `value={"ADMIN"}` 角色约束）。前端路由通过 `router.beforeEach` 守卫配合 `route.meta.requiresAuth/requiresAdmin/requiresGuest` 实现页面级权限控制。

微信登录采用 OAuth2 授权码流程：前端通过 `qrcode` 库生成带 state 参数的微信扫码 URL，轮询 `/api/auth/wechat/check?state=xxx` 等待用户扫码确认，后端在微信回调中通过 code 换取 access_token 和用户信息，关联到本地 User 表后签发 JWT。

### 安全机制清单

| 机制 | 实现 |
|------|------|
| 密码加密 | BCrypt |
| 无状态认证 | JWT HMAC-SHA，7天有效 |
| 接口拦截 | AuthInterceptor + @RequireAuth |
| 角色控制 | USER / ADMIN 两级 |
| 微信登录 | OAuth2 + QR 码轮询 |
| 邮件验证 | QQ SMTP + Console 降级 |
| CORS | WebConfig 全局配置 |
| 前端路由守卫 | router.beforeEach 检查 meta |

## 十四、关键设计决策

回顾整个项目，有七项决策深刻影响了架构走向和运维体验：

1. **零 Python 依赖**。a-stock-data Skill 定义的接口原为 Python 实现，本项目全部用 Java RestTemplate 直连重写。这意味着后端容器无需安装 Python 运行时，部署镜像精简，运维面收窄到 JVM 单一运行时。

2. **MySQL + Redis + Caffeine 三级缓存**。如果只用 Redis 作为缓存，高频访问场景下网络 IO 仍是瓶颈（~1ms）；引入 Caffeine 本地缓存（<1μs）作为 L1 缓冲层，将热数据的读取延迟降低三个数量级。MySQL 作为 L3 不仅提供持久化兜底，也为数据清理和回溯查询提供 SQL 能力。

3. **定时拉取而非实时透传**。外部 API（尤其是东方财富系列）存在不稳定的限流策略，如果每次前端请求都透传到外部 API，一旦外部故障则整个页面白屏。定时异步拉取 + 多级缓存的方式将外部依赖隔离在后台，用户始终从缓存读取，可用性由缓存保证。

4. **数据定期清理**。A 股数据具有天然的时效性衰减——昨天的快讯今天价值有限，一周前的龙虎榜基本无参考意义。通过凌晨清理任务分级设置保留时长（3 天 / 7 天 / 30 天 / 365 天），在保留足够回溯能力和控制数据库增长之间取得平衡。

5. **前端 IntersectionObserver 懒加载**。首页 9 个数据模块全部加载会同时触发大量 API 请求，IntersectionObserver 按视口可见性分批触发，首屏仅加载 3 个模块，折叠线以下模块滚动到附近才请求。这项设计显著降低了首屏白屏时间。

6. **Maven 多模块分层**。common（Entity/DTO）→ service（Mapper/Service）→ start（Controller/Config/Scheduler）的依赖方向确保了模型可被任意上层模块复用，业务逻辑独立于 Web 层可单元测试，启动配置集中在 start 模块便于环境切换。

7. **Docker Compose 单机部署**。项目规模不需要 Kubernetes 的编排能力，Docker Compose 管理 4 个服务容器足够简洁。桥接网络 + 命名卷 + depends_on 启动顺序 + MySQL init scripts 自动建表，实现了一行 `docker compose up -d` 完成全部部署。
